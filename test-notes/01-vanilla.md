## 0. 结论速览

**一句话：窗口内 15 个原版版本全部跑完、每版 17 条 CLI/网关用例 0 失败；唯一的功能性问题（游戏内 `#` 聊天不被转发）在 15 个版本上表现完全一致，因此它不是一个“版本兼容性”问题，而是与「离线模式 + 默认 `chat` 模板」的组合有关（根因留给汇总卡）。**

- **覆盖**：15 个版本 × 17 条 CLI/网关用例 = **255 条，全部 PASS**；另每版各跑一次 C19（真 QQ 网关 `run` + 真实客户端进服/聊天/退服 + 日志轮转 + SIGTERM）与 C20（真实聊天行喂模板 A/B）。
- **跨版本一致（15/15 版都对）**：服务端启动与 RCON 连通、`check`（QQ 真探活 + 真 RCON + 日志可读）、`commands`、`bind set/list`、QQ→MC 真注入 `tellraw`、`/status` 真往返、未绑定/非前缀/未知指令/缺参数/非法 ID 五条边界文案、多行只转发第一行、健康翻转三条、旧格式聊天行转发、回环防护、进服事件模板、**进服/退服通知真的走到 QQ 平台**、**日志轮转（S6）后不丢事件**、**SIGTERM 退出码 0**。
- **跨版本一致的唯一功能失败**：`F-V1` —— 游戏内 `#` 聊天在**所有 15 个版本**上都不会被转发到群（默认 `chat` 模板匹配不上真实行）；把模板放宽（**只改配置**）后同一批真实行立刻能转发。窗口内**没有**“从哪一版开始变的”边界（1.21.2 起就已经是这个格式）。
- **一次运行期异常**：`F-V2` —— 1.21.8 首跑时 QQ 网关启动失败（平台 `/gateway/bot` 请求超时 → 进程报 `[错误]` 后立即收尾）；同版本复跑 + 3 次冷启动尝试（`_gateway-restart/`）**都没再出现**，按“一次性/未复现”登记，原始输出见 `artifacts/vanilla/1.21.8/run.out.gateway-starttimeout-original.txt`。
- **两处覆盖缺口**（不是缺陷）：26.2/26.3 没有可用的无头客户端（mineflayer 支持的版本上限是 26.1），真玩家侧用 `docs/smoke.md` §5 的手工法（往 `latest.log` 追加真实格式行）补测，事件 3/3 通过；真群收发（`group_openid` 未知）与正版（`online-mode=true`）聊天行格式本环境无法覆盖 —— 见 §7。

## 1. 测试版本清单与理由

### 1.1 为什么是这 15 个版本

任务要求是「近两年发布的 Java 原版服务端，**只要 x.xx.0，不需要细化到 x.xx.xx**」。
这句要求在 Minecraft 的版本号体系里**没有字面对应物**：原版用的是 `1.21.2`（三段式，但从来没有 `1.21.0`），
2026 年起的版本号是 `26.1 / 26.1.1 / 26.2 / 26.3`（年份.序号），也没有 `26.1.0` 这种形态。
`00-env.md` §3 已经把这层事实写清楚（并从 Mojang 版本 JSON 抓到了每个版本要求的 `javaVersion`）。

因此本卡把它落成可执行的口径，并且**两层都做了**：

1. **主矩阵 = 每条“版本线”的首个正式版**（8 个）——对应“不要细化到 x.xx.xx”的本意：
   `1.21.2`、`1.21.4`、`1.21.5`、`1.21.6`、`1.21.9`、`26.1`、`26.2`、`26.3`。
   判定依据是**版本号形态 + 与前一版的发布间隔**（同日或十几天内、且只递增末位的，视为上一条线的补丁版）——
   这是本卡的判断，不是 Mojang 官方口径（没查发布说明）。**但这不影响结论**，理由见下一条。
2. **其余 7 个补丁版也一并实跑**（`1.21.3`、`1.21.7`、`1.21.8`、`1.21.10`、`1.21.11`、`26.1.1`、`26.1.2`）。
   原因很具体：`00-env.md` §7-10 抓到一条现场证据（1.21.11 的聊天日志行与项目默认 `chat` 模板不匹配），
   并**明确把「具体从哪个版本开始变的」留给矩阵卡判定**。要回答这个问题，就必须把补丁版也跑一遍；
   而每个版本的成本只有约 2 分钟（见 §2.3），值得。

**所以本卡的清单 = 窗口内（2024-10-18 起）全部 15 个正式版**：既满足“不必为每一条线的每个补丁出结论”的要求，
又把版本边界问题一次答完。（窗口起点前最近的一版 `1.21.1`（2024-08-08）不在窗口内，未测。）

### 2.2 本卡新增的测试脚手架（已入库到 `test-notes/scripts/`）

| 文件 | 作用 |
|---|---|
| `vanilla-matrix.sh` | **单版本执行器**：建/复用实例 → 起服务端 → 生成该版的机器人配置 → 跑 C1–C20 → 起真实客户端 → 归档制品 → 停服回收 |

每版机器人的配置由脚本生成（`~/Y33-Bot/config-vanilla-<版本>.toml`），要点：

- `[[mc_servers]].name` = `v1_21_2` 这类（配置的 `name` 只允许 `[A-Za-z0-9_-]`），`port` = 该版 RCON 端口，`log_path` 指向该版 `logs/latest.log`；
- **每版独立的 `state` 文件**（`data/state-vanilla-<版本>.json`）与独立 `bindings` 文件 —— 沿用 `00-env.md` §4 的坑 2（共用状态文件会互相污染日志偏移）；
- `group_openid` 用假群 `E2E_DUMMY_GROUP_OPENID`（与 `00-env.md` §7-8 同一手法）：让 MC→QQ 方向真的打开、真的走到 QQ 平台，平台必然回 400（“群不存在”），从而让发送链路留下可判读的痕迹，同时不打扰任何真实群；
- `[log_patterns]` 用 `config.example.toml` 的**默认值**（这是“项目默认配置”的基线），另有同一份配置但把 `chat` 模板放宽的 `config-vanilla-fix-<版本>.toml` 专门用于 A/B 对照（**只改配置不改代码**）；
- `health_poll_interval = 3600`（避免健康轮询噪声干扰），健康翻转用 `simulate health` 单独测（C13–C15）。

### 2.3 成本实测（每版一个循环）

- 单版循环实测 **约 95 秒 ~ 5 分钟**（受同机其它矩阵卡争内存影响；无争抢时 ≈95s），其中服务端首次启动
  （建世界 + 解压 libraries）18–61s，`Done (...)` 后 RCON 端口立即可连；
- 磁盘：单版峰值约 110M（jar 56M + libraries 45M + world 5M），每版跑完即回收，测试全程 `/` 可用空间稳定在 1.2–1.6G；
- 15 个版本的完整矩阵（含 1 次重跑）在 **2026-10-18 14:49 → 15:3x** 之间跑完（见 §4 每版时间戳）。

### 6.2 结论

1. **窗口内没有“版本相关”的差异**：13 个能用真客户端跑完的版本，行为逐条一致；
   `00-env.md` §7-10 留给矩阵卡的悬案（“聊天行格式从哪一版开始变”）答案是：
   **从窗口最早的一版（1.21.2，2024-10-22）起就已经是 `[Server thread/INFO]: [Not Secure] <player> …`，
   窗口内每一版都一样，变更点在窗口之前（≤ 1.21.1）**。
2. **默认 `chat` 模板在本环境的实例设置下（`online-mode=false`）对 1.21.2–26.3 全部失效**；
   放宽模板（只改配置）后全部可用，且不影响普通聊天忽略、回环防护、进出服通知。
3. **RCON 方向（QQ→MC）在 15 个版本上完全可用**：真 `tellraw` 注入、真 `/list` 往返、真 `/status` 渲染。
4. **运行期健壮性**（本卡顺手覆盖的 S5-8 / S6 部分）：真实玩家进服/退服 → 事件进发送路径（平台回 400 属预期）；
   清空 `latest.log` → 偏移重置且不丢事件；SIGTERM → `[停止] 已退出` + 退出码 0。
5. **没有观测到** 崩溃、卡死、RCON 协议不兼容、日志解析越界等情况；15 版 255 条 CLI 用例 0 失败。
